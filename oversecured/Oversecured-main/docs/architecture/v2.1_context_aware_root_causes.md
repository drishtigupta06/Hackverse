# v2.1 — Context-Aware Root Causes

## The Two-Graph Model

### Graph 1 (Existing — Detection Graph)
```
Code/Maniest → Finding → Root Cause
```
Detector-centric. Knows *what* is wrong, not *where* it's exploitable.

### Graph 2 (v2.0 — Trust Graph)
```
Component → Trust Boundary → Protection Level → Escalation Path
```
Structure-centric. Knows *where* the trust boundaries are, not which findings cross them.

### The Gap
v2.0 proved these are independent layers:

- `LastAccessedProvider` is **protected** (signature-gated), but no MF/ADV finding references it by component
- `ArchivesProvider` is **protected** (MANAGE_DOCUMENTS), and MF-011/MF-072 match it, but through `exported=true` not through the permission boundary
- Finding-centric shielding (`shield_findings`) is a compatibility shim — it works when findings happen to carry component names, fails when they don't

## v2.1 Target: Merged Model

```
Component
  ├── Trust Boundary         (from SystemAnalyzer)
  ├── Root Cause             (new: component-centric)
  ├── Findings               (evidence, not identity)
  ├── Escalation Paths       (cross-component chains)
  └── Validation Status      (live test results)
```

### Core Data Structure

```python
@dataclass
class RootCause:
    id: str                          # ROOT-017
    component: str                   # com.android.documentsui.archives.ArchivesProvider
    component_type: str              # provider | activity | service | receiver
    trust_boundary: TrustBoundary    # from trust_boundary_engine
    protection: str                  # signature | system | none | uri_grant
    exploitability: str              # blocked | conditional | open | validated
    severity: str                    # critical | high | medium | low
    evidence: list[Finding]          # findings that demonstrate the issue
    escalation_paths: list[str]      # chain IDs that include this component
    validation: dict                 # live test results
```

### Root Cause Generation (new algorithm)

Instead of grouping findings by regex-matched ID patterns (ROOT_CAUSES table):

1. **For each exported/accessible component** identified by `SystemContext`:
   - Query all findings whose `matches` or `source_location` references this component
   - Query all ADV/SRC findings in code paths that flow into this component
   - Attach the **trust boundary** from `TrustBoundaryEngine`
   - Compute **exploitability**: if trust boundary is non-bypassable → `blocked`

2. **Exploitability Rules**:
   - `permission_boundary` + non-bypassable → `blocked`
   - `uri_grant` → `conditional` (requires requesting app to hold grant)
   - `unprotected_exported` → `open`
   - `shared_uid` → `conditional` (requires same-signature app)
   - PoC executed successfully on live device → `validated` (overrides all above)

3. **Evidence Collection (Weighted Model)**:
   - Simple regex matching between findings and components produces too much noise.
   - Each linking signal gets a weight; findings attach only above threshold:

     | Signal | Weight | Condition |
     |--------|--------|-----------|
     | `component_name` match in finding | 50 | exact match between finding field and component FQN |
     | Manifest reference | 40 | finding's `matches` contains `<provider|activity name='...'>` for this component |
     | Call graph edge | 30 | source analysis traces invocation path into component's handler |
     | Taint path sink | 60 | data flow analysis confirms untrusted input reaches component entry point |
     | Live validation | 100 | `service call`, `content query`, or `adb shell am` confirms access |

     `sum(weights) >= 50` → finding attached as evidence.

   - A finding can be evidence for multiple components (e.g., `intent redirection` may affect all exported activities).
   - The root cause is the component + its trust boundary, not the finding pattern.

### Precision Impact

Current (v1.5):
```
DocumentsUI: 20% (3/15 RC validated)
Dialer: 31.3% (5/16)
Aggregate: 26.3% (20/76)
```
False positives come from findings about components behind signature gates.

v2.1 projection:
- `blocked` components (signature/privileged-gated, non-bypassable) → excluded from exploitable count
- `conditional` components (URI grant, shared UID) → partial confidence, counted but penalized
- `open` components (unprotected exported) → full exploitable, highest confidence
- `validated` components (live PoC confirmed) → 100% confidence, gold standard

Target: 50-60%+ precision (from 26.3% baseline).

This is realistic because signature-protected components currently sit in the `exploitable` bucket. Moving them to `blocked` removes the largest source of false positives. The remaining headroom comes from better evidence linking (weighted model filters out weakly-associated findings).

The precision ceiling is ultimately bounded by the trust boundary engine's accuracy, not by finding detection sensitivity.

## Implementation Plan

Priority order — escalation path validator depends on correct component-trust-boundary root causes, so it comes last.

### Phase 1: ComponentRootCause dataclass
- Define `RootCause` dataclass with component, trust_boundary, exploitability, evidence, validation
- Deprecate `ROOT_CAUSES` static table — replace with dynamic generation from `SystemContext` components

### Phase 2: Exploitability Scoring
- Map each trust boundary type to exploitability state (`blocked`/`conditional`/`open`/`validated`)
- Scoring function that downgrades blocked RCs from exploitable count
- `validated` state set by live validator results, overrides all other states
- After this, `shield_findings()` is no longer needed (exploitability lives on the component, not the finding)

### Phase 3: Evidence Linker — Weighted Model
- Implement scoring pipeline with threshold-based attachment
- Source 1: manifest `matches` field (weight 40)
- Source 2: finding field `component_name`/`name`/`description` (weight 50)
- Source 3: call graph paths into component handler (weight 30)
- Source 4: taint flow sinks at component entry points (weight 60)
- Source 5: live validation results (weight 100)
- Threshold `>= 50` — configurable, tune per corpus

### Phase 4: Remove `shield_findings()`
- Compatibility shim is obsolete once exploitability lives on the component
- All downstream consumers (report, metrics, chains) read exploitability from `RootCause.exploitability` directly

### Phase 5: Re-run DocumentsUI
- Single-app validation: measure precision delta from 20%
- Verify that `ArchivesProvider`, `LastAccessedProvider`, `PickCountRecordProvider` are correctly `blocked`
- Verify that unprotected exported activities (PickActivity, LauncherActivity) are correctly `open`

### Phase 6: Re-run 22 APK Corpus
- Full batch evaluation with v2.1 pipeline
- Measure precision improvement from 26.3% baseline
- Per-app breakdown: which precision gain came from trust boundaries vs. better evidence linking

### Phase 7: Escalation Path Validator
- Only after root causes are component-centric
- Each escalation path step maps to a RootCause component
- `blocked` components break chains (path cannot start or pass through)
- `validated` components confirm chain feasibility
- `open` components are likely chain starting points but need validation
- Validate chains with `service call`/`content query`/`adb shell am` on live device

## Why Not More Detectors

Detection appears saturated. Adding more YAML rules or XPath patterns will find more findings but won't fix the precision bottleneck. The bottleneck is structural: the scanner models code, not Android's permission model. v2.1 bridges that gap.

## Migrating From v2.0

What stays:
- `SystemContext` (Phase 1) — component extraction
- `TrustBoundaryEngine` (Phase 2+3) — boundary detection
- `SignatureAnalyzer` (Phase 4) — permission classification
- `SystemValidator` (Phase 6) — live validation
- Report template sections for trust boundaries

What changes:
- `RootCauseDedup` → replaced by component-centric root cause generation
- `shield_findings()` → removed (no longer needed; exploitability is per-component)
- `RootCauseEngine` (benchmark) → frozen as v1.5 baseline reference

What's new:
- `ComponentRootCause` class
- Evidence linker (findings → components)
- Exploitability scoring module
- Escalation path validator
